ZERO DEPENDENCY HACKATHON 2026 ADAPTIVE LOSSLESS COMPRESSION SUITE
COMPLETE EXECUTION WORKFLOW
============================================================

Document purpose

This document replaces the earlier “format extension -> preset codec”
workflow with a more adaptive compression architecture.

The original project direction was: FILE TYPE -> COMPRESSION PROFILE ->
COMPRESSION STRATEGY -> .ZC

The revised direction is: FILE -> CONTENT PROFILING -> CANDIDATE
GENERATION -> OPTIONAL REVERSIBLE TRANSFORM -> STANDARD-LIBRARY CODEC ->
FULL .ZC SERIALIZATION -> FINAL ARCHIVE SIZE COMPARISON -> BEST VALID
REPRESENTATION -> .ZC -> VERIFIED RESTORATION

The goal is not to promise that every file becomes smaller. The goal is
to make the compressor intelligently determine when and how compression
is useful, while guaranteeing exact byte-for-byte recovery.

============================================================ 2. PROJECT
PITCH ============================================================

Recommended project identity:

    ZeroShrink
    Adaptive Lossless Compression - Zero Dependencies

Pitch:

    "ZeroShrink profiles the actual byte structure of a file, applies
     reversible preprocessing when useful, automatically selects an
     appropriate standard-library compressor, and stores the result in a
     custom .ZC archive with integrity verification."

The important difference from the original project is that file
extensions are no longer treated as the main compression decision.

An extension or file signature is only one input to the decision system.

The actual bytes determine which compression candidates are worth
trying.

============================================================ 3. WHY THE
ORIGINAL APPROACH GIVES DIMINISHING RESULTS
============================================================

The original architecture used:

    TXT  -> ZSTD
    PDF  -> ZSTD
    PNG  -> ZSTD/STORE
    JPEG -> ZSTD/STORE
    MP4  -> ZSTD/STORE

This is useful as a product demonstration, but it does not create much
additional compression because:

1.  File extensions do not describe the statistical structure of the
    bytes.
2.  PNG, JPEG and MP4 commonly contain already-compressed data.
3.  Huffman alone is not competitive with mature LZ-based compressors on
    general-purpose data.
4.  RLE is specialized and should not be treated as a universal codec.
5.  Running every compressor against every file wastes CPU and memory.
6.  Comparing only compressed payload size can select a codec whose
    final .ZC archive is actually larger than STORE.
7.  A custom archive has metadata overhead, which matters especially for
    small files.

Therefore the new architecture must first determine what kind of data it
has before deciding which transformations/codecs to run.

============================================================ 5. CONTENT
PROFILER ============================================================

The profiler should be cheap.

Do not read a huge file six times just to decide whether it should be
compressed.

For large files, inspect: - beginning sample - middle sample - ending
sample

Combine samples into a bounded profiling buffer.

Suggested profiling fields:

    File size
    Extension
    Magic/signature
    Entropy estimate
    Unique byte count
    Byte diversity
    Printable-byte ratio
    Run ratio
    Repetition estimate
    Binary/text likelihood
    Already-compressed likelihood
    Possible structure alignment

  -------------
  5.1 Entropy
  -------------

Estimate Shannon entropy:

    H = -sum(p_i * log2(p_i))

where p_i is the frequency of byte value i in the sample.

Interpretation:

    Low entropy:
        more predictable data
        potentially more compressible

    High entropy:
        often already compressed/encrypted/random-like
        STORE may win

Do not use entropy as a mathematical proof that compression will fail.
Use it as a candidate-selection heuristic.

  --------------------
  5.2 Byte diversity
  --------------------

Calculate:

    unique_byte_count / 256

Examples:

    Text:
        often significantly below 1

    Random/encrypted/compressed:
        often close to 1

Again, this is a heuristic.

  ---------------
  5.3 Run ratio
  ---------------

Measure consecutive repeated bytes.

Example:

    AAAAAAAAAAAAAAAAAAAAA

has high run potential.

Random data has low run potential.

High run ratio makes: RLE -> ZSTD

a candidate worth testing.

  ---------------------
  5.4 Printable ratio
  ---------------------

Approximate:

    printable_bytes / sample_size

High printable ratio suggests text-like content.

Use this to generate text candidates, not to force a particular codec.

  ----------------------
  5.5 Repetition score
  ----------------------

Estimate repeated short sequences.

The purpose is to detect: repeated tokens repeated records repeated
binary structures repeated blocks

High repetition strongly suggests LZ-style compression may work well.

  -----------------
  5.6 Magic bytes
  -----------------

Recognize common signatures where practical:

    PNG:
        89 50 4E 47 0D 0A 1A 0A

    PDF:
        %PDF-

    JPEG:
        FF D8 FF

    MP4:
        basic ftyp-box inspection

Also recognize already-compressed containers when feasible:

    ZIP
    GZIP
    XZ
    ZSTD
    etc.

Do not build complete parsers.

  -----------------------------

    BZ2

  -------------------------------------
  6.2 Example: highly repetitive data
  -------------------------------------

Candidate set:

    STORE
    ZSTD

  ----------------------------------------
  6.3 Example: structured numeric binary
  ----------------------------------------

Candidate set:

    STORE
    ZSTD
    DELTA + ZSTD
    SHUFFLE32 + ZSTD
    SHUFFLE64 + ZSTD

  --------------------------------------
  6.4 Example: already-compressed JPEG
  --------------------------------------

Candidate set:

    STORE
    ZSTD

If profiling strongly indicates high entropy and an already-compressed
signature, do not waste time running LZMA, BZ2, Huffman and RLE.

  --------------------------------------------
  6.5 Example: random/encrypted-looking data
  --------------------------------------------

Candidate set:

    STORE
    possibly one quick ZSTD test

If ZSTD is not smaller after accounting for archive overhead, select
STORE.

============================================================ 7.
REVERSIBLE TRANSFORMS
============================================================

The important conceptual change is:

    Transform != compression codec

A transform rearranges or represents the same information in a form that
a compressor can exploit better.

Every transform MUST have an exact inverse.

The pipeline becomes:

    original
       |
       v
    reversible transform
       |
       v
    ZSTD/LZMA/etc.
       |
       v
    compressed payload

During decompression:

    compressed payload
       |
       v
    codec decompression
       |
       v
    inverse transform
       |
       v
    original bytes

============================================================ 8. DELTA
TRANSFORM ============================================================

For byte data:

    y[0] = x[0]

    y[i] = (x[i] - x[i-1]) mod 256

Example:

    Input:
        100 101 102 103 104 105

    Delta:
        100 1 1 1 1 1

The transformed data contains repeated small differences that ZSTD can
compress efficiently.

Inverse:

    x[0] = y[0]

    x[i] = (x[i-1] + y[i]) mod 256

Test requirements:

    empty input
    one byte
    constant data
    increasing sequence
    decreasing sequence
    random bytes
    all 256 byte values
    round-trip equality

============================================================ 9. RLE
TRANSFORM ============================================================

Do not treat RLE as the main general-purpose compressor.

Use it as a preprocessing transform:

    raw
      ->
    RLE representation
      ->
    ZSTD

Example:

    AAAAAAAAAAAAAAAAAAAAA

becomes a representation equivalent to:

    (A, 21)

The representation must include enough information to distinguish
literal data from run records.

If the transformed representation becomes larger than the original, the
candidate can be discarded.

Test:

    empty
    one byte
    one long run
    alternating bytes
    random data
    multiple runs
    invalid encoded data
    round-trip equality

============================================================ 10. BYTE
SHUFFLE TRANSFORM
============================================================

For structured binary values, rearrange bytes by position.

Example for 32-bit records:

    A1 B1 C1 D1
    A2 B2 C2 D2
    A3 B3 C3 D3

becomes:

    A1 A2 A3
    B1 B2 B3
    C1 C2 C3
    D1 D2 D3

This can expose low-variance byte planes.

Candidate variants:

    SHUFFLE32 + ZSTD
    SHUFFLE64 + ZSTD

Only attempt this when profiling suggests structured binary data.

The transform metadata must record the word size and enough information
to reverse the operation exactly.

============================================================ 11.
STANDARD-LIBRARY CODECS
============================================================

Use standard-library compression facilities wherever possible.

Primary codecs:

    ZSTD
    LZMA
    BZ2
    zlib

Custom codecs:

    Huffman
    RLE

STORE:

    identity/no compression

Python 3.14 provides Zstandard in the standard library through
compression.zstd, alongside standard compression modules.

Important: Do not implement ZSTD or LZMA yourself.

The custom implementation value should come from: profiler candidate
selector transforms .ZC format verification integration

============================================================ 12. COMMON
CODEC INTERFACE
============================================================

All codecs should have a consistent internal abstraction.

Conceptually:

    compress(input) -> compressed representation
    decompress(compressed) -> original representation

For large files, prefer streaming interfaces.

The implementation should not force every file into memory.

Suggested abstraction:

    Codec
        id
        name
        compress_stream(...)
        decompress_stream(...)
        supported_options(...)

For small fixtures, a bytes-based convenience path is acceptable.

============================================================ 13.
STREAMING ARCHITECTURE
============================================================

Large files can be several gigabytes.

Avoid:

    data = file.read()

followed by several copies of data.

Instead:

    input file
       |
       v
    chunk reader
       |
       v
    transform
       |
       v
    streaming codec
       |
       v
    temporary candidate file
       |
       v
    candidate size

Candidate files should be temporary.

After selecting the winner: delete all rejected candidates retain only
the winner finalize the .ZC archive

This prevents large memory spikes.

============================================================ 14.
CRITICAL SELECTION RULE
============================================================

NEVER choose the winner solely by compressed payload size.

Wrong:

    candidate A payload = 98 KB
    candidate B payload = 100 KB
    choose A

because the final archive may have different metadata sizes.

Correct:

    original
       ->
    candidate transform
       ->
    codec payload
       ->
    complete .ZC serialization
       ->
    final archive byte size

Then:

    winner = smallest valid complete .ZC archive

Example:

    Original:
        100 KB

    ZSTD payload:
        98 KB

    ZSTD .ZC:
        104 KB

    STORE .ZC:
        101 KB

Winner:

    STORE

This rule is extremely important for small files.

============================================================ 17.
INTEGRITY AND CORRUPTION HANDLING
============================================================

Treat every .ZC archive as untrusted input.

Validation order:

    1. minimum archive size
    2. magic
    3. version
    4. flags
    5. profile ID
    6. transform ID
    7. codec ID
    8. filename length
    9. metadata length
    10. payload boundaries
    11. decode
    12. original size
    13. CRC32
    14. SHA-256

Possible errors:

    Invalid ZeroShrink archive.
    Unsupported archive version.
    Unknown codec.
    Unknown transform.
    Invalid metadata.
    Unexpected end of archive.
    Decompressed size mismatch.
    CRC verification failed.
    SHA-256 verification failed.

Never write the final restored file before verification succeeds.

Use: temporary file verify atomic/collision-safe final move

============================================================ 18. CRC32 +
SHA-256 ============================================================

CRC32: fast corruption detection

SHA-256: stronger content identity verification

Store the hash of the ORIGINAL file.

After decompression:

    restored_sha256 == original_sha256

Display:

    CRC32: PASS
    SHA-256: PASS
    BYTE-FOR-BYTE RESTORATION: PASS

This gives the demonstration a strong verification story.

============================================================ 19. FILE
TYPE HANDLING
============================================================

The application may still offer:

    Text
    PDF
    PNG
    JPEG
    MP4
    Any File

But these are now user-facing profiles, not hard-coded compression
rules.

Example:

    User chooses PNG

The application: checks extension/signature profiles the bytes
determines that PNG is already compressed tries only sensible candidates
selects STORE if no useful gain exists

The system should never claim:

    "PNG always compresses with ZSTD."

Instead:

    "PNG detected. Additional byte-level compression appears unlikely.
     STORE selected because it produced the smallest valid .ZC."

============================================================ 20.
SMALL-FILE HANDLING
============================================================

Small files may become larger because of:

    archive header
    filename
    metadata
    hash
    codec overhead

Therefore:

    final .ZC size is the only metric that matters for selection.

For very small files:

    STORE will often win.

This is correct behavior.

Do not force compression simply because the user selected “Compress.”

============================================================ 21.
LARGE-FILE HANDLING
============================================================

For large files:

    1. profile a bounded sample
    2. generate a small candidate set
    3. use streaming codecs
    4. write candidates to temporary files
    5. compare final sizes
    6. retain only winner

Optional optimization:

    For very large files, stop testing a candidate when its current output
    already exceeds the best known complete representation by enough that
    it cannot possibly win.

This is an optimization, not an MVP requirement.

============================================================ 40. FINAL
PRODUCT PHILOSOPHY
============================================================

The project should no longer be presented as:

    "A Huffman compressor that accepts different file extensions."

It should be presented as:

    "An adaptive, lossless compression engine that analyzes the actual
     structure of a file, chooses a small set of appropriate compression
     candidates, optionally applies reversible transformations, selects
     the smallest complete .ZC representation, and verifies exact
     restoration - using only the Python standard library."

The most important behavior is honesty:

    If data compresses well:
        show the gain.

    If a transform improves compression:
        show the transform.

    If ZSTD is best:
        use ZSTD.

    If LZMA/BZ2 is better:
        use it.

    If a custom transform wins:
        use it.

    If the input is already efficiently compressed:
        choose STORE.

    If archive overhead makes compression pointless:
        choose STORE.

    If the archive is corrupted:
        reject it.

    If restored bytes differ:
        report failure.

This makes the project useful rather than merely demonstrative.
